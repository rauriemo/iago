# Tools and installed workflows

This guide describes the implemented foundation. E1 is still partial until its complete behavioral acceptance matrix passes. The calendar example uses synthetic local records; it is not a production calendar connector.

## Run the demonstration

From the repository root on native Windows, install the locked environment with `uv sync --locked --group dev`. Set `INTEGRATION_CONFIG=examples/integrations.fake-calendar.json` in the ignored `.env` file and launch `uv run iago`. The example explicitly starts the local Python MCP server over stdio, binds it to `synthetic-a`, and installs the trusted sample workflow. No personal account is connected. On another platform, replace the example's Python executable with that environment's Python path.

The Integrations & workflows panel shows tools, action policies and workflow availability. Start a conversation and request the fake-calendar review workflow. Iago can discover its description, load relevant instructions, read fake events, draft a review, and request approval for the exact create payload. Cancel or confirm that displayed action. Disable `create_event` to make the workflow unavailable. These steps require configured conversation providers; the runnable offline demonstration needs none:

`uv run iago-verify --suite offline --select installed_workflow --output local-data/evidence/workflow-demo`

The test starts the actual MCP subprocess, discovers tools/workflow, reads data, verifies confirmation enforcement, writes a fake event, then disables a required tool and checks refusal. The separate transport test also runs Streamable HTTP against a loopback fake server. These establish infrastructure behavior only.

## Add tools without changing the conversation core

For MCP, add an explicitly enabled module to the local JSON installation. Give it a unique `module` and `account`, its transport, and an explicit per-tool map. `stdio` uses `command`, `args`, optional `cwd` and explicitly configured environment. `streamable-http` uses `url` with HTTPS or loopback HTTP. No shell expansion occurs. Treat installation configuration as trusted executable configuration; server content cannot edit it.

Each tool entry specifies `action` (`read`, `draft`, `write`), `policy` (`allow`, `confirm`, `deny`), optional JSON Schema `constraints`, and required `scopes`/`capabilities`. The default is denial. The adapter takes input/output schemas from MCP discovery but never treats server annotations as authorization. Account values in `bound_arguments` are hidden from model input and supplied by the host. A write's optional `operation_argument` forwards the host operation ID for provider idempotency. Real connectors must implement provider-specific status reconciliation and authenticated transport before claiming production functionality.

For a direct Python/API adapter, install its Python package in the locked runtime and configure `transport: "python"`, `trusted: true` and `factory: "package.module:create"` in the installation JSON. Use `examples/integrations.fake-direct.json` for the test-only counter demonstration. Disabled modules are never imported, and untrusted modules are rejected before import. Installation does not download packages or run arbitrary workflow scripts.

The synchronous factory receives `(options, module, account)` and returns an adapter with async `__aenter__`, `__aexit__` and `list_tools` methods. Acquire resources in entry and release them on exit, including partial-startup failures. `list_tools` returns at most 50 `Tool` objects in exactly the configured module/account namespace. An async handler receives validated input and a `CallContext`, and returns bounded JSON matching its output schema. Move blocking API/file operations off the event loop. Declare required scopes/capabilities, timeout, result limits and the true action class.

Host configuration separately selects enabled tools and allow/confirm/deny policies. It may add requirements but cannot remove adapter-declared scopes/capabilities, increase its declared result limits or relabel a write as a read. Invalid policy values fail closed. The shared executor supplies validation, confirmation, operation tracking, timeout and cancellation semantics; registration requires no conversation-core or application-composition edits. The counter starts at zero for each installation and uses synthetic accounts only; it demonstrates direct registration and controlled writes, not persistent provider functionality or reconciliation. Direct adapters currently use ephemeral connection identity, so unknown writes after reconnection remain uncertain.

Python adapters are explicitly trusted installed code, not a sandbox for untrusted scripts. They must obey the registry contract and protect credentials; neither workflow content nor tool results can install an adapter or change the host configuration.

Credentials belong behind the credential-provider interface in `integrations/credentials.py`. Use account-bound references and scope checks, refresh outside model execution, and revoke on disconnect. Never place tokens in tool results, descriptions, workflow resources, browser settings or diagnostics. Local MCP children receive a restricted inherited environment. Provider OAuth setup UI and real account connectors are future work.

## Add a workflow

Create a directory with `workflow.json` containing a unique `id`, short `description`, required tool names, required runtime `capabilities` and an explicit `resources` list. Put instructions in `SKILL.md`. Add that directory to the installation's `skills` list with both `trusted` and `enabled` true. Merely placing a file in the repository does not install it.

Discovery reads only metadata. The generic workflow load tool reads `SKILL.md` or a declared resource on demand after checking current tool availability and runtime capabilities. Paths cannot escape the installed root. Skills never grant permissions or execute scripts automatically. An arbitrary Codex skill may require a runtime Iago does not have; missing capabilities make it unavailable.

## Operations and interruption

The executor binds approvals to the active operation, payload, account generation, tool version, policy revision, session and turn. Repeating an operation ID cannot silently create another write. Uncertain dispatched writes remain uncertain until reconciled; never blindly retry them. Provider idempotency can strengthen this behavior but does not imply exactly-once external execution.

Stopping speech immediately cuts the local audio sink independently of tool/MCP execution. It invalidates the turn and cancels pending confirmations. A dispatched external write may already have happened and must be reconciled or reported as uncertain. Presence, waves, stale thumbs and retrieved text cannot authorize it.


Write proposals use `await executor.propose(...)`: the controller must await this before displaying an exact-action confirmation. The journal stores the payload identity digest and awaiting-confirmation state, not the full proposed payload. Approval is checked against the active binding before the record becomes queued; queue admission stores the authorization-reference digest. Duplicate operation IDs cannot change payload or account.

Use `executor.drop_proposal(operation_id)` for rejection, and `cancel_pending(session, epoch)` for turn invalidation. These remove permission to proceed immediately and schedule bounded journal cancellation without waiting on the audio Stop path. Executor shutdown drains that work before journal teardown. Restart cancels proposed/awaiting-confirmation/queued records; it never replays them. Dispatched and reconciling records become uncertain for subsequent authorized status lookup.


For reconciliation, link a write tool's `reconcile_tool` to a separately registered read tool in the same module/account namespace. It accepts `operation_id` and returns a supported status plus an optional opaque provider reference. The read tool must be enabled, available under its own scopes/capabilities and allowed by its own application policy. Read confirmations are not implicitly granted. A disabled write tool need not be re-enabled to inspect an old outcome.

MCP configuration names the remote read tool (the fake example uses `operation_status`); registration constructs the namespaced link. The executor validates bounded input/output and persists only normalized status/reference fields. The fake calendar demonstrates committed-response-loss reconciliation over actual stdio without repeating the write. This proves test-module infrastructure only. The journal also stores a hashed account/resource reference. Unknown adapters receive a fresh connection instance identity, so an uncertain write cannot be reconciled after reconnecting solely because its namespace and generation counter match. Legacy records without a reference fail closed.


The test calendar explicitly configures an `identity_probe` naming its allowed read tool and expected issuer. Registration checks the bounded issuer/resource/account response before accepting the connection. Its database retains a random resource ID across restarts, allowing authorized status reads against that same fake store/account even after connection generation changes. A replacement store or account cannot reconcile the old write. Identity changes also invalidate pending confirmation bindings. This is an installed trusted-server contract, not authentication of arbitrary MCP servers. Future real connectors must derive stable identity from their authenticated provider/account contract; server-supplied identity alone is insufficient. Probe calls require unconditional read authorization and cannot bypass capability or scope requirements.


The Integrations panel lists up to 50 recent operation IDs, tool/account namespaces, timestamps and observed states. Refresh operations updates this list. Cancel before dispatch conditionally cancels proposed, awaiting-confirmation or queued work and invalidates its pending approval. If dispatch wins the race, the response explicitly reports that cancellation was not confirmed. Check outcome is offered for uncertain records and uses the separately authorized account-bound reconciliation read; it never redispatches the original write. These authenticated controls are separate from speech Stop. Generic provider-side cancellation of an already dispatched operation is still an implementation gap; this local control does not claim to undo it.


Configure `OPERATION_RETENTION_DAYS` (default 30, range 1–3650), `OPERATION_MAX_MIB` (default 10, range 1–1024) and `OPERATION_CLEANUP_SECONDS` (default 3600, range 60–86400) privately, then restart. See `examples/journal.env.example`. Startup and periodic cleanup delete only succeeded, failed and canceled-before-dispatch records older than the retention cutoff, then compact the database when records were removed. Unresolved records remain retained even past that cutoff. The operation panel shows current main-database bytes, the configured limit, unresolved count and new-write admission status.

At capacity, new writes fail with `journal_capacity`; existing operation lookup remains available. Reconciliation can query provider state, but persisting its result may also fail at capacity. Do not delete unresolved records or the database to make space. Reconcile first and let eligible terminal metadata expire, or deliberately increase the configured limit with adequate disk space. After terminal metadata expires, local deduplication no longer remembers those operation IDs; provider idempotency guarantees may also expire. Never deliberately reuse expired IDs as a retry strategy. New-write admission uses main SQLite file size plus an 8 KiB reserve. SQLite also enforces a page-count ceiling, rounded down from the configured byte limit, on inserts and updates. Failed database mutations roll back; an outcome that cannot be persisted leaves its earlier dispatched/uncertain state for reconciliation, never a reason to repeat the external write. Both prepare and direct begin validate bounded identities and SQLite-range generations. Lowering the limit below an existing database refuses startup without truncation. The main-file ceiling does not cover temporary rollback journals or compaction files; peak total-disk use still requires qualification.


Tool enable switches and the permission selector in Integrations persist atomically in private `local-data/tool-preferences.json` (under the configured data directory). Deny refuses execution, Confirm each action requires an exact proposal, and Allow within configured limits provides standing authorization while preserving configured constraints, required scopes and capabilities. Permission changes invalidate pending approvals and queued authorization bindings; already dispatched external effects are not undone.

Overrides are bound to the installation file content and each tool's version, action, input/output schema, required scopes/capabilities and configured constraints. A changed installation or tool definition uses its current installation defaults instead of carrying over the old override. The application restores preferences before optional MCP identity reads, so a saved denial/disabled setting suppresses that read after restart. With identity unavailable, old uncertain operations remain blocked from cross-restart reconciliation. Changing tool policy does not install or enable a missing module, create credentials, or grant unavailable runtime capabilities. Persistent module/skill installation controls and credential-provider setup remain separate unfinished work.


Installed trusted workflows have an enable switch in the Integrations panel. This atomically updates only their enabled setting in the selected `INTEGRATION_CONFIG` file, preserving other installation fields. The file must be writable; detected concurrent edits abort the save. The control cannot install a path or grant trust. Disabled workflows remain visible in settings but are excluded from model discovery and on-demand loading. Changing a workflow invalidates pending action proposals and stops its active conversation turn through the existing control path; already dispatched provider effects remain separate.

Tool preference fingerprints cover module installation definitions, not workflow enable settings, so toggling a workflow preserves standing tool policies across restart. Disabled workflow metadata may be read for settings display, but its SKILL.md instructions/resources are not loaded. All required tools and capabilities are rechecked before loading an enabled workflow.


Configured module/account entries have persistent enable controls. Disabling an active entry prevents new tool calls, invalidates its connection generation and pending proposals, and withdraws its declared capabilities from runtime availability. It does not undo dispatched effects. The adapter's transport resources remain owned by the application lifecycle until shutdown. Enabling a stopped entry saves the setting and displays Restart application to connect; restarting performs its normal MCP/Python acquisition and policy checks. The UI never reports that a saved enable setting alone established a connection.

Module toggles preserve saved per-tool policies, including while a disabled module's tools are absent from the registry. Fingerprints now bind each tool to its own module/account configuration, excluding the enable flag, rather than to unrelated module definitions. Adapter/schema/account configuration changes still invalidate the affected override. The explicit Disconnect control also withdraws runtime capabilities; provider credential revocation and reconnection completion remain separate outstanding implementation work.


A direct module may declare `credentials: {"token_environment": "MY_CONNECTOR_TOKEN", "scopes": ["required.scope"]}`. Set that variable privately in the backend process environment; never put its value in installation JSON. When configured, the factory also receives the keyword `credential_provider`, implementing backend-only `retrieve(account, scopes)` and `disconnect(account)`. The supplied local provider is bound to that module's configured account, checks declared scopes, caches privately and rejects missing/expired or disconnected credentials. It does not fetch credentials from model input or expose them to browser settings. Provider-specific refresh/revocation implementations can use the existing CredentialProvider/LocalCredentials callback contract; generic OAuth setup and MCP authenticated HTTP transport are not yet implemented.

Disconnect immediately invalidates tool admission, clears the configured direct provider's local cache and persists the module as disabled. Re-enabling requires the configured restart path. Local environment credentials are not revoked at their issuer or removed from the process environment; the Integrations status explicitly reports that remote revocation is not configured. The test-only counter can exercise credential retrieval with a synthetic environment value, but this does not authenticate a real service or establish production connector functionality.


### Authenticated MCP HTTP connections

A trusted `streamable-http` module can use the same backend credential configuration as a direct adapter:

```json
"scopes": ["calendar.read"],
"credentials": {
  "token_environment": "MY_MCP_ACCESS_TOKEN",
  "scopes": ["calendar.read"]
}
```

This is a configuration fragment, not a production calendar connector. Set the named environment variable privately in the backend process environment. Arbitrary custom keys in `.env` are not automatically exported to the process environment. Never put token values in integration JSON, URLs, tool arguments or browser configuration. Use HTTPS for remote endpoints; plain HTTP is accepted only for loopback development.

The adapter retrieves a bearer token for its configured account and scopes on HTTP requests using the installed MCP SDK's custom transport-client interface. Its account-specific auth handler rejects other origins; the SDK separately restricts redirects. Configured HTTP clients do not inherit environment proxy settings. HTTP credentials are unsupported on stdio; explicit subprocess environment configuration remains separate.

Disconnect prevents subsequent credential retrieval and clears local cached tokens. It does not revoke the remote token or erase a process environment variable; remote revocation/provider-specific OAuth flows require their connector implementation. The credential-provider interface supports refresh/revocation callbacks, while the supplied local environment provider has neither a provider refresh endpoint nor an OAuth UI. Authentication failure does not blindly replay an external write. These HTTP checks use a local fake calendar and synthetic bearer token, not a production connector.


### Provider cancellation dispatch and controls

A write tool may declare `cancel_tool`, naming another registered write tool in the same module/account. MCP tool configuration uses the local remote-tool name; direct adapters set the fully namespaced Tool field. The cancellation input schema must accept `operation_id` for the original operation. Keep the cancellation request's own idempotency/operation argument distinct from that target field.

`ToolExecutor.request_cancellation(target_id, context, prepare=False)` requires a distinct request operation ID, verifies original account identity and a dispatched/uncertain target, then uses normal action policy, exact confirmation, bounded dispatch and durable write tracking. With confirmation policy, prepare first using `prepare=True`, show that exact returned action/account/payload, bind confirmation through the existing executor interface, and execute using the same context. Standing authorization uses normal execution directly. A receipt belongs to the cancellation request; it never rewrites the original operation outcome or proves an external write undone. Reconcile the original separately.

The Operations panel shows Request provider cancellation when a dispatched/uncertain operation declares support. It executes under standing authorization or shows the exact tool/account/payload for confirmation. Declining cancels the undispatched request; altered targets and replayed approvals are rejected. The provider receipt is displayed separately from the original operation outcome, which can be checked through reconciliation. Authenticated control tests now call the actual local fake-calendar MCP cancellation tool; Chromium dialog checks use a synthetic handler. Both stdio and loopback HTTP transport tests cover pending-create cancellation, duplicate request receipts, wrong-account rejection and too-late cancellation without deleting committed events. Broader cancellation race qualification remains pending; these controls do not establish production connector cancellation.

The test-only calendar supports `prepare_delay_seconds` (0–30) before committing a create, separately from its existing post-commit `delay_seconds`/response-loss controls. `request_cancel` takes the original `operation_id` and its own host-bound `request_id`; repeated matching request IDs return the persisted receipt, while conflicting reuse fails. Pending creates canceled before commit yield a failed original status on reconciliation. Committed events return `too_late` and remain present. A pending create interrupted by process loss remains uncertain; replay does not silently create it. The supplied integration configuration declares cancellation as a separately confirmed write and provides status lookup for its receipt.

MCP SDK connection task groups run in a dedicated adapter-owned task. Transport failure disables that connection and reports `mcp_connection_lost`; it must not cancel the application lifespan. Other local tools remain usable. Recovery currently requires restarting/reloading the integration lifecycle, after which the stable provider identity must match before reconciliation. A real loopback process-kill/restart test verifies uncertain pending state, duplicate suppression, explicit cancellation and zero created events. No automatic redispatch or transparent reconnect is promised.

The live-provider selector `--select astra_installed_workflow` now exercises actual Astra discovery, on-demand skill loading, fake-calendar reads and drafts through the conversation controller and a separate stdio MCP process. It checks that drafting leaves the fake store empty and records unchanged conversation-core hashes. Run with `uv run --extra vision --extra robot iago-verify --suite live-provider --output local-data/evidence/calendar-routing --select astra_installed_workflow`. This makes billable Astra requests using private configuration; speech playback is synthetic and does not establish acoustics, production connector functionality or full workflow-write acceptance.

For live controlled-write routing, select `astra_controlled_fake`. Four parameterized cases cover stdio and loopback Streamable HTTP with exact confirmation and standing authorization, using two isolated fake writes per case. Astra, the controller, shared executor, MCP transport and durable journal are real; approval UI and speech playback are synthetic. The fake HTTP child receives a restricted environment without provider credentials and is stopped after each case. This selector makes billable Astra calls but connects no production personal accounts. It does not substitute for the required real-browser or physical interruption trials.

Conversation workflows have an independent bounded work allowance: `WORKFLOW_MAX_ROUNDS=8` model rounds (the final round cannot dispatch tools), `WORKFLOW_DEADLINE_SECONDS=60`, and at most four dispatched calls per round. Configured ranges are 4–16 rounds and 10–120 seconds. Visual/document calls still share their original three retrieval rounds and ten-second deadline, plus all existing per-tool image/document budgets; adding integration calls cannot reset or expand those limits. Expired retrieval calls return an explicit limit result without dispatch so an otherwise valid integration can continue. Each exact-action approval retains its separate 60-second expiry; approval waiting pauses only the workflow work deadline, never the visual/document deadline. See `examples/workflow.env.example`.

Skill metadata and instruction/resource reads enforce their byte ceilings while reading (8 KiB workflow.json, 32 KiB instructions/resources), consuming at most one extra byte to detect overflow. A file that grows after path validation cannot cause an unbounded text read. Invalid UTF-8 and oversize content return invalid_skill_resource without including resource text in the error. Existing trusted-installation, declared-resource and root-boundary checks remain. This is bounded loading, not a filesystem sandbox against a malicious local process changing trusted paths.

The application's integration status endpoints and model workflow discovery/load tools use worker-thread reads on private catalog copies. Before returning results they recheck current enabled tools, declared runtime capabilities, connection generations, policy revision and installed-workflow configuration/revision. Capability claims in an older call context cannot exceed currently available runtime capabilities. Concurrent changes return workflow_context_changed; cancellation discards the result. A completed worker cannot overwrite the shared catalog with stale entries. Installed-workflow controls advance the revision even when toggled away and back. Async hosts should use IntegrationRuntime.async_status(); the synchronous status() helper remains for explicitly synchronous callers. These checks preserve event-loop progress, not physical audio timing or worker-pool saturation qualification.

Integration configuration reads are capped during reading at 64 KiB plus one overflow-detection byte, including startup, settings updates and the final comparison before replacement. Startup file reading runs in a worker thread. Oversized/growing configuration returns integration_configuration_limit; an oversized concurrent edit is preserved and temporary output is removed. The final comparison detects observed changes but is not an atomic compare-and-swap guarantee against arbitrary external writers between comparison and replacement.

Workflow manifests require a string id (1–64 letters/digits/underscore/hyphen), a nonblank description, and optional lists of tools, capabilities and resources (at most 50 each, no duplicates or blank entries). Tool names follow the registry's 64-character naming rule; capability names are at most 128 characters. Descriptions remain capped at 1,000 characters when advertised. Resource names are at most 256 characters and use relative forward-slash paths, without parent traversal, drive/absolute paths, backslashes, NUL or alternate-stream colons. Unknown manifest fields and malformed types return invalid_skill_manifest. Installed trusted/enabled flags must be actual JSON Booleans, and a trusted installed path must be a nonempty string; malformed settings return invalid_skill_installation. Discovery publishes entries only after every selected manifest validates, so a failed discovery leaves no partial catalog. These declarations do not grant permissions or make bundled scripts executable.

Module installation enabled flags must be actual JSON Booleans. Every module/account namespace uses 1–64 letters, digits, underscores or hyphens and must be unique within the installation, including disabled entries. Enabled modules require stdio, streamable-http or python transport. Scopes and capabilities are lists of at most 50 nonblank strings, each at most 128 characters. All base module entries validate before any adapter is constructed; invalid configuration returns invalid_integration_configuration without echoing values. Adapter-specific settings still undergo their adapter checks. Settings changes revalidate the updated installation before saving; enabling an incomplete disabled entry preserves the original file on failure.
