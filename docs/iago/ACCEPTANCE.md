# Iago acceptance contract

This document makes the Revision 6 acceptance matrix executable. SPEC.md sections 2, 17 and 18 remain authoritative. The initial FEATURES.json is a tracking manifest, not an implemented test suite. No application checks have run in this handoff package.

## Evidence and status

Maintain all 36 feature IDs (C1-C9, V1-V9, P1-P10, D1-D6, K1 and E1). For each feature, link implementation paths, test/scenario IDs and evidence. Track implementation as `not_started`, `partial` or `implemented`; track each validation tier independently as `not_run`, `pass`, `fail` or `blocked`. A blocker needs its prerequisite and the exact step that will resolve it.

Use these validation tiers:

| Tier | What it can establish |
| --- | --- |
| offline | Deterministic core/protocol/storage tests, browser automation, fake device/provider integration, prerecorded perception tests and build checks; each check declares its inputs |
| live_provider | Actual configured Astra, transcription and both speech adapters; authentication, formats, streaming and failures where reproducible |
| live_pc | Native Windows setup and physical webcam/microphone/speakers; representative whiteboard/phone material and acoustic measurements |
| robot | Real Reachy media, stop, motion, Wi-Fi failure and onboard resource qualification |

Prerecorded perception fixtures may be real recordings or synthetic inputs; record which. Neither proves live room performance by itself. Browser automation with virtual devices does not qualify physical acoustics. A successful API response does not prove that audio played.

The manifest supplies minimum tier assignments; expand test cases to cover the full specification. `pass` is local to the evidence's declared environment and dataset. Do not aggregate a feature to fully validated while one of its required tiers is blocked, not run or failed. Tests must assert observed outcomes, not only that a mocked method was called.

## Required verification entrypoint

During implementation, add one documented command with suite selectors for `offline`, `live-provider`, `live-pc` and `robot`. Choose the runner that fits the repository. It must produce both machine-readable results and a concise Markdown report. No runner is included in this planning package.

Reports must contain: source commit and dirty-tree status; date; suite/scenario/feature IDs; exact command; platform, browser, devices, dependency and model versions; fixture IDs; configuration without secrets; sample counts; expected and observed values; status; evidence paths; blockers. Include selected voice ID where safe, without credentials. Keep latency traces, logs and recordings distinguishable from summaries generated by an LLM.

A requested suite returns success only when its required checks pass. Missing prerequisites produce an explicit unavailable/blocked result and a non-success exit for that requested suite. Running only offline checks can succeed as an offline run, but cannot report full release acceptance. Automated CI should run the offline suite; run applicable live suites in the environment that has their prerequisites.

Create the harness and representative failing cases before implementing the corresponding behavior. Grow tests alongside each milestone. Do not require every future test to exist before building the first vertical slice. Track test corrections separately from product scope changes. Do not lower thresholds or remove difficult cases to pass.

## Behavioral gates

1. **Cancellation and history.** Inject interruption during recognition handoff, Astra streaming, tool lookup, TTS setup, synthesis, fallback and buffered playback. Assert the sink flush, epoch/generation rejection and no old speech after reconnection. Interrupt a multi-item answer after item one; subsequent context must exclude unheard items. Include late provider chunks and overlapping stop/finish events.
2. **Voice selection and failure.** Verify OpenAI-only operation; valid ElevenLabs key and chosen voice select ElevenLabs; invalid settings and runtime failures follow the specified fallback policy. Fail a provider before audio and after partial audible output. Never replay the partially heard answer. Both voice paths remain interruptible.
3. **Physical speech.** On the actual PC speakers, run ten minutes of assistant output with zero self-triggered turns and at least 20 spoken interruptions. Preserve the user's opening words. Measure physical cutoff using a separate recording/loopback path: explicit Stop p95 under 150 ms and spoken interruption p95 under 300 ms are targets, not existing results. Report median, p95, slowest and sample counts for both providers and a fallback attempt. Do not infer speaker silence from a cancellation acknowledgment alone. Report ordinary response latency separately from history lookup; proposed ordinary-turn targets are median under three seconds and p95 under five seconds.
4. **Visual grounding.** Build at least ten representative whiteboard/phone scenarios, including show-then-lower, before/after board revisions, references near minutes 1/5/9, fine-text crops, blur/glare, upload fallback and expired images. Score reference selection, exact reading, uncertainty and reasoning separately. Evidence IDs and timestamps must identify the actual inspected source. An LLM rubric may supplement these checks; it cannot replace objective retrieval/reading labels or user assessment of brainstorming usefulness.
5. **Storage and timing.** With a controlled clock, cross both age and byte limits; prove deletion, pin bounds and bounded work. Camera off clears camera evidence, Stop sharing clears screen evidence, and Clear/End clear all transient visual evidence; removed evidence and derived context must never re-enter. Inject clock offset, delay and reconnect; associations remain valid or are explicitly uncertain. Cancel while decoding or retrieving.
6. **Perception and initiative.** At least ten controlled entries; at least 20 real wave clips and 20 negatives, including static hands, drawing, phone use and camera movement. Initial wave gate: at least 90% recall and at most one false trigger in that negative set, plus a natural 30-minute desk observation with false-event counts. Keep the small-set claim distinct from general accuracy. Test sustained gestures, occlusions and event storms. Test confidence, persistence, enable/disable, mode, quiet times, cooldown, expiry, interruption backoff and speech priority deterministically. Aware must make no continuous cloud transcription/reasoning calls; an enabled greeting must transition correctly into and out of conversation.
7. **Lifecycle and product.** Exercise microphone/camera denial, unplug, browser reload/close, sleep/resume, provider loss and bounded reconnection. Verify real UI state, device selection, notes/export/delete, camera controls, evidence correction and usage accounting. Run a 30-minute real PC product demonstration and a 90-minute soak; report bounded queues/storage and memory after warmup. Record representative provider usage as specified, subject to the configured development budget.
8. **Reachy.** Implement fake-edge tests now for leases, stop generations, late epochs, disconnection, clock mapping and ownership. Implement real adapters and deployment packaging now using verified official contracts. Later run current video, detailed snapshots, mic, both voices, physical stop, PC disconnect and motion interference on the actual robot. Qualify standalone capability and effective rates on hardware; do not claim standalone full-rate performance from PC measurements.

## Revision 5 additional gates (planning only)

All original eight behavioral gates and SPEC.md section 18 gates remain mandatory. The datasets below are additional; they do not replace whiteboard/phone, wave, acoustic or robot evidence. These are requirements for future runnable tests, not existing fixtures or passes. Freeze fixture IDs, labels, expected passages and scoring before the scored run; keep tuning material separate. ### P10 - thumbs as question responses

- P10-MEDIA: at least 20 real thumbs-up examples, 20 real thumbs-down examples and 20 negatives, each labeled with source, person count, question state and expected outcome. Use varied hand orientation, distance and light. Negatives include neutral/open hands, waves, pointing, drawing, phone use, camera motion and ambiguous/multiple people. Record accepted controller turns, not just classifier output. Proposed initial gates: >=90% recall for each thumb class (at least 18/20 each), <=1 false response in the 20 negatives, and zero wrong-polarity accepted answers. Larger datasets preserve percentage gates and report counts; false-response gate remains <=1 for the declared negative set. Report missed/suppressed cases explicitly. The small-set gate is not a claim of general accuracy.
- P10-POLICY: deterministic fixtures must cover long holds spanning two questions; release and rearm; gesture held before question; confidence/stability boundaries; no question; question replacement/expiry; disabled setting; both hands conflicting; multiple people; tracking loss; stale/out-of-order/source-generation events; simultaneous and delayed speech; Stop/End; camera loss; and rejected screen, upload and historical inputs. Each case must assert exact accepted turn counts, values, question IDs and cancellation effects. All assertions must pass; no unauthorized or duplicate turn is allowed. Test at least 5 event-order permutations for speech/gesture, question replacement and cancellation races.
- P10-UI: toggle, current question, recognized/accepted/ignored feedback and diagnostic injection are observable. Synthetic test mode cannot enter the production conversation. Re-run the existing wave dataset unchanged to detect regressions.
- Evidence: offline uses deterministic events and explicitly labeled prerecorded clips; live_pc requires a separate live-webcam run of the same minimum counts through the real controller and feedback. Live-provider checks verify Astra receives one associated yes/no user turn. Robot qualification repeats the counts on the real Reachy camera, including clock delay and motion interference; PC results cannot qualify it.

### V9 - continuous screen sharing

- V9-GROUNDING: at least 12 real PC screen scenarios: 3 current-view questions, 3 historical references near minutes 1/5/9, 2 fine-text/crop tasks, 2 simultaneous-camera tasks with deliberately similar content, 1 pinned-screen-after-rolling-expiry case and 1 source-change case. Exercise each monitor/window/tab source type offered by the tested browser; document browser-specific unavailable choices instead of claiming coverage. Define at least 20 exact text labels, expected sources/times and reference frames before testing. Require >=90% exact labels (18/20 for the minimum set), correct evidence/source selection in all 12 cases, valid provenance on every citation, and no invented text on separate unreadable/blank examples.
- V9-LIFECYCLE: deterministic/browser tests cover user activation/picker cancellation, permission denial, capture ending, reload, source replacement, screen audio absence, concurrent camera, shared byte/pin limits, per-source sampling, Stop sharing, Camera off, Clear and End. Run at least 2 assertions/cases per category: normal completion and an in-flight frame/retrieval race. All must pass with no old-generation evidence restored, no thumb/wave turn from screen/history/upload input, and no duplicate audio ownership. Stop sharing clears only screen evidence; Camera off clears only camera evidence; Clear/End clear all transient visual sources, leaving project indexes separate.
- V9-CANCEL: interrupt during capture upload, preview/decode, historical lookup, crop inspection and model follow-up; assert zero late speech/evidence from the canceled generation. Permission denial or capture loss preserves an otherwise usable conversation. Re-test screen browser loss in reachy_pc without ending the robot audio session.
- Evidence: offline browser/fake-source contracts cannot establish real picker permissions or readability. Run the 12 scenarios and permission/capture controls in live_pc with actual sharing and Astra (also linked to live_provider). Robot suite verifies assisted camera plus PC share, stop/ownership behavior, and explicit screen unavailability without a PC sharing session in standalone mode. No PC-off screen capability may be reported.

### K1 - document corpus, questions and hard gates

Create a versioned, non-secret evaluation corpus of at least 3 isolated projects with 10 supported files each (30 supported files total). Each project contains at least 2 Markdown, 2 TXT, 2 text-PDF, 2 DOCX and 2 source/configuration text files. Across projects include Python/JS and JSON/YAML/TOML examples, duplicate relative filenames, overlapping vocabulary and contradictory project facts. Each PDF has at least 3 pages and each DOCX at least 3 named sections. Add at least 12 exclusion/unreadable fixtures beyond those 30: 2 scanned PDFs, 1 mixed text/scanned PDF, 1 malformed DOCX, 1 encrypted/unreadable PDF, 1 unsupported binary, 2 dummy credential files, 2 dependency/generated artifacts and 2 outside-root link/junction/traversal cases. Dummy secrets must be synthetic labels.

- K1-RETRIEVE: 30 answerable questions (10/project), each with independently labeled supporting passage IDs and answer facts. Include a second paraphrased wording for at least 15 of these, yielding at least 45 scored query variants. At least 6 questions span two passages. All five supported format categories must be represented in the query set. Require gold support in the top 8 retrieved passages for >=90% of variants (at least 41/45) and >=90% of the paraphrased subset (at least 14/15). For multi-passage questions a hit requires all necessary gold passages, not just one.
- K1-CITE: Every factual answer must include supporting citations and visible snippets covering its answer facts; omission is a failure, not a vacuous citation pass. 100% of returned citations must resolve to the selected project, existing relative file path, correct content revision and truthful available page/section/line locator. Snippets must match that revision's extracted source text. Missing locators are declared, never invented. For actual Astra answers require >=90% supported correctness across answerable query variants and zero fabricated citations or unsupported factual assertions. Abstention may count as an incorrect answer for the correctness gate, not as a fabricated assertion. Score facts with human-authored labels, not model self-grading alone.
- K1-ABSENT: at least 10 additional questions whose answers are absent from the active project, including at least 4 with answers only in a different configured project. All 10 must explicitly report absent/insufficient evidence with no invented answer or citation and no cross-project leakage.
- K1-UPDATE: at least 12 controlled operations: 3 edits, 3 moves, 3 deletions and 3 creations spread across projects. After each operation, read/search must never serve stale/deleted content; moves retire old citations. On the idle desktop, each stable change must appear in status/index within the proposed 5-second target or be recorded as a failure. Reindex, project switch/removal, restart persistence and removal during indexing each get a deterministic case; all pass with original files unchanged and removed records never restored by a late worker.
- K1-BOUNDARIES: all 12 extra fixtures receive correct exclusion/error/partial/OCR status; no scanned-only PDF is marked successfully indexed, no dummy credential text appears in index/results, and no out-of-root access succeeds. Verify limits on files, bytes, extraction expansion/time, queries/passages and active-project generations. Cancellation during parsing, search, passage read, reformulation and model streaming yields zero stale tools, snippets or speech; all assertions pass.
- K1-UI: real UI permits root configuration, active-project choice, progress/errors, supporting snippets, Reindex and Remove project; correctly explains durable indexing versus transient visual context and leaves original files untouched on removal.
- Evidence: offline runs the fixed corpus/contract/parser tests with labeled expected results. live_provider runs actual Astra queries/citations; live_pc runs the complete query set and project controls through the real conversation UI against configured PC fixtures, including at least 10 spoken queries. robot verifies the same source restrictions and retrieval on configured robot-accessible fixtures, resource limits and source-unavailable behavior, and assisted access to configured PC fixtures. Do not assume PC folders exist onboard.

### Mixed workload, timing and resumption

Include the additions in the existing 30-minute product demonstration and 90-minute soak without dropping old tasks. During at least 60 minutes of the desktop soak, keep camera and screen active, run both wave and thumb processing, maintain the 30-file document corpus, perform at least one change/reindex batch per 10 minutes, and alternate camera/screen/document queries at least once per 5 minutes. Exercise all 12 document mutations during the run. Include at least 20 valid thumb responses and 20 speech interruptions; existing both-voice/fallback acoustic gates remain required.

Report median/p95/slowest and counts separately for gesture recognition/commit, source capture/archive, document search/read/reindex, combined evidence retrieval and physical audio. Preserve original <150 ms Stop / <300 ms spoken-interruption p95 targets and ordinary-turn latency gates under the added load. Report retrieval separately under its configured 10-second deadline. Require bounded queues, global visual/pin budgets, separate index cap and no monotonic memory growth after warmup. Robot soak qualifies its explicitly configured sources/rates; no active PC means no PC-screen workload. Keep physical robot/PC and automated evidence distinct.

Wake-word detection is excluded. Verify existing manual start and visual triggers still work; do not create wake-word tests or implement a detector. The reserved future word is Iago, named after the Aladdin parrot.

## Revision 6 E1 gates (requirements for implementation)

Retain all eight original gates, every P10/V9/K1 dataset above, and all SPEC.md section 18 gates. Implement the following as runnable behavioral checks in the required verification entrypoint, with scenario IDs and reproducible observed evidence. All assertions are mandatory. Planning files, interfaces and fake data alone are not passing checks or production connector functionality.

- **E1-TRANSPORT:** Launch the test-only fake calendar using the selected maintained MCP SDK in a separate stdio process and as a loopback Streamable HTTP server. For each transport assert negotiated initialization, discovery, bounded read, draft, authorized create, denied create, typed error and shutdown by inspecting returned records and fake-store changes. Record SDK/protocol versions and redacted traces. No mocked transport counts as a round trip. Two synthetic accounts have distinct records; no real calendar/email/WhatsApp account is connected.
- **E1-REGISTRY:** Register the calendar and a direct adapter by configuration/package discovery without changing the conversation core (record before/after core hashes). Exercise existing visual/document/notes tools through the shared executor with original budgets and source/project generation rules. Assert namespace collision rejection, disabled-module/tool omission from model discovery and denial of manually submitted disabled calls, including disable after discovery. No disabled call changes the fake store.
- **E1-SCHEMA:** Supply malformed inputs/results, oversized results, over-limit concurrency and missing runtime/tool/scope capabilities. Assert typed bounded errors, no invalid dispatch or result delivery, no secret values in model input/browser/logs, and useful status. Required scripts without their runtime cannot execute. Verify stricter visual/document bounds remain intact.
- **E1-ACCOUNTS:** With two fake accounts and separate grants, assert reads, drafts, writes, token retrieval/refresh and disconnect are isolated. Account A grants cannot authorize B; drafts cannot send. Revoke a scope or disconnect between discovery, confirmation and dispatch; assert no undispatched write and no stale result enters the active turn. Remote revocation failure must be visible. Use synthetic sentinel tokens to detect leakage in all output surfaces.
- **E1-SKILLS:** Discover an explicitly installed trusted sample SKILL.md and reject an untrusted/uninstalled package. Assert only descriptions/metadata load initially, relevant instructions/resources load on demand, unrelated resources remain unread, traversal/oversized resources fail, and only enabled tools with available capabilities execute. A skill attempting to enable itself/tools or expand authorization must fail.
- **E1-CONFIRM:** Assert an allowed read, local draft, denied write, exact confirmed write and write within standing authorization; standing authorization must not prompt repeatedly. Mutate each of operation ID, tool/version, account/generation, payload, policy revision and expiry after proposal; each invalidates approval. Assert replay, canceled/superseded proposals, presence, waves, fresh conversational thumbs and stale gestures cause zero unauthorized writes. User-speech/question ownership must remain intact.
- **E1-LIFECYCLE:** Use deterministic barriers/clocks to test timeout before and after dispatch, cancellation before dispatch, during provider work and after completion, duplicate concurrent requests, mismatched reuse of operation ID, restart and late results. Run at least five orderings of cancellation/dispatch/confirmation/disconnect races. Assert exact fake-store mutation counts, durable outcomes and no old speech. Canceling undispatched work makes zero changes; stopping speech must not falsely report an in-flight write undone.
- **E1-RECONCILE:** Simulate write committed then response lost, write not committed then connection lost, and crash around dispatch, both with and without provider idempotency support. Reopen the durable journal and reconcile against fake provider state. Assert at most the authorized mutation, no blind retry, truthful uncertainty when status is unavailable, and eventual correct outcome when status returns. Duplicate requests reuse the operation outcome; conflicting payloads fail. Test retention/capacity, unresolved tombstones and redaction without storing sensitive full payloads. No exactly-once claim beyond demonstrated provider guarantees.
- **E1-INJECTION:** Place instructions to change permissions, expose tokens, switch accounts or send unauthorized events in retrieved documents/messages, calendar tool results and workflow resources. Assert permissions remain unchanged, tokens never enter model/browser/log output, and fake-store changes remain zero without independent valid authorization.
- **E1-EVENTS:** Feed duplicate, stale, reordered and old-account-generation fake external events plus fresh events during quiet hours, cooldowns and user speech. Assert exact accepted/suppressed counts, bounded pending work, no unapproved writes and no speech-priority bypass. No real webhook, scheduler or background notification service is required.
- **E1-PRIORITY:** Block MCP reads/writes, credential refresh, skill resource loading and reconciliation while interrupting audio. Deterministic checks assert immediate local sink invalidation, epoch rejection and robot-local stop/watchdog independence. In the existing live-PC both-voice/fallback physical cutoff trials, include each blocked activity and report median/p95/slowest with unchanged <150 ms Stop / <300 ms spoken-interruption p95 gates and no restarted speech. Repeat robot-local independence on hardware; fake edge checks do not pass physical robot gates.

Evidence tiers: offline covers real local MCP transports with explicitly fake calendar/provider data and deterministic policies. live_provider verifies actual Astra discovery/tool/workflow routing and real voice interruption while the calendar stays fake. live_pc exercises integration settings, exact-action UI, read/draft/controlled-write workflow and physical audio. robot verifies configured runtime/capability availability, source restrictions and local stop independence. No production personal connector tier is claimed from this demonstration; missing prerequisite checks are blocked, never passed.

Include the E1 sample workflow in the existing 30-minute product demonstration without dropping prior scenarios. During the existing 90-minute soak run at least one fake calendar read/draft/controlled-write cycle per ten minutes, alternating transports, and inject delayed calls/reconciliation during the required interruptions.
