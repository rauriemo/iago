# Iago build instructions

Merge these instructions into the repository's AGENTS.md, preserving existing applicable instructions. The launch goal also explicitly loads this file, so it can be used before that merge.

Iago implements the complete first release in `docs/iago/SPEC.md`, Revision 6. The specification's review-stage wording describes when it was written; a user issuing the supplied build goal authorizes implementation. The name Iago does not change the feature scope.

Before implementation, inspect the actual repository and applicable instructions, then read SPEC.md, ACCEPTANCE.md, FEATURES.json and PROGRESS.md in `docs/iago/`. Read the specification in chunks if necessary; do not rely on a truncated tool response. Preserve existing user work. Record the initial branch, commit and dirty files before editing.

Implement all 36 feature IDs: C1-C9, V1-V9, P1-P10, D1-D6, K1 and E1. Milestones organize execution; they do not reduce scope. Continue through implementation, debugging, relevant verification and documentation. Make routine reversible implementation decisions and record their reasons. Ask only when a missing decision materially blocks further useful work; finish independent work first.

Keep Astra as the application brain, ElevenLabs with the configured voice as primary when valid, and OpenAI speech as default/fallback. Verify current official APIs, installed versions and model access before relying on them. A different coding model or reasoning setting does not change Iago's runtime brain configuration. Do not silently substitute a model when access is missing.

Preserve the architectural invariants: native Windows PC operation with real browser devices; optional robot dependencies; separate recognition, reasoning and synthesis; local sink interruption and epoch rejection; heard-answer context; bounded visual history and explicit pins; independent archive and detector rates; temporal waves; restrained configurable initiative; one media/motion owner; robot-local stop supervision.

Follow the acceptance contract. Create runnable checks and a reproducible evidence report; a checklist is not a test. Keep implementation state separate from validation state. Missing credentials, fixtures or hardware are `blocked`, never `pass`. Do not skip or weaken a requirement to obtain green results. Correct an erroneous test transparently, retaining the original requirement and explaining the correction.

Use deterministic tests for races and policy. Use real providers, representative recordings and physical devices for the claims that require them. Label synthetic media and mocked providers explicitly. Redact secrets and keep personal recordings out of Git by default. Read credentials from local configuration; never print them or include them in browser bundles.

Update `docs/iago/PROGRESS.md` and `FEATURES.json` after each meaningful milestone, with actual commands, evidence paths, failures and the next step. Implement the verification entrypoint defined in ACCEPTANCE.md and record its exact invocation. On resumption, inspect code and recent results before trusting the progress file.

Before handoff, review the entire diff against the specification, fix material findings and run the affected checks. Deliver launch/setup instructions, locked dependencies, real adapters, configuration examples, acceptance evidence and pending physical checks. Do not mark the full product validated while mandatory gates are blocked or failing. Missing Reachy hardware cannot justify leaving implementable robot integration as a placeholder.

Revision 6 also requires context-bound thumbs-up/down user input from live cameras only, continuous visual-only desktop sharing alongside camera with source-scoped clearing and shared global visual budgets, and read-only configured-project indexing/search with bounded cited passages. Preserve waves, speech priority, question/turn ownership, source/project generations and cancellation. Project indexes are durable and separate from transient visual history; enforce folder/exclusion boundaries and remove-project deletion without editing originals. PC screen and PC folders require their configured PC sources; document standalone limitations.

Retain all original acceptance gates and the concrete P10/V9/K1 datasets in ACCEPTANCE.md. Run all runnable required evaluations and fix failures; synthetic, skipped or unavailable checks never count as physical passes. No wake-word detector is in scope; the future selected word is Iago, named after the Aladdin parrot. Planning amendments do not authorize execution of the build goal or imply implementation/test progress.

E1 requires working shared tool execution, maintained MCP SDK stdio/Streamable HTTP transports, direct adapters, private credential-provider interfaces, trusted on-demand skills, per-tool/account policies, exact-action confirmations, durable uncertain-write reconciliation and bounded event ingress. Keep immediate local audio stop and robot supervision independent of integrations. Honor standing authorization; skills and retrieved content cannot grant permissions, and conversational gestures cannot authorize external writes. Deliver minimal controls, extension documentation and the test-only fake calendar/sample workflow, demonstrating registration without conversation-core edits. Real calendar/email/WhatsApp accounts and production connector services remain later work. Retain all E1 behavioral gates alongside earlier acceptance datasets; actual transport behavior needs runnable checks, and fake data never proves production connector functionality.
